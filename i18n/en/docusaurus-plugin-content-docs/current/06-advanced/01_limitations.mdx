# Known Limitations

Please review the requirements and limitations below before using the SDK.

## Device Requirements

| Item | OpenCL minimum | OpenCL recommended |
|------|-------------|-------------|
| **Android version** | 8.0 (API 26) | 12+ (API 31) |
| **RAM** | 4 GB | 6 GB or more |
| **Storage** | 500 MB | 1 GB or more |
| **GPU** | OpenGL ES 2.0 / OpenCL 1.2 | OpenGL ES 3.0+ / OpenCL 2.0+ |

## Supported Architectures (ABI)

| ABI | Supported | Notes |
|-----|----------|------|
| `arm64-v8a` | Supported | Most modern devices |
| `armeabi-v7a` | Supported | Older 32-bit devices |
| `x86_64` | Not supported | Emulator |
| `x86` | Not supported | Emulator |

:::warning Emulator caveats
The SDK does not work on x86/x86_64 emulators.

**How to test:**
- Use a real Android device (recommended)
- Use an ARM-based emulator (for example, the default emulator on Apple Silicon Macs)
:::

## Network Requirements

### Mandatory Conditions
- **Internet connection**: Required for real-time WebSocket communication
- **Protocol**: HTTPS / WSS (TLS 1.2 or higher)
- **Port**: 443

### Firewall Configuration
```
# Domains that must be allowed

```

### Network Permissions
```xml

<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />
```

## Audio-related Limitations

### USB Microphone Compatibility

- **MMAP policy**: MMAP is managed internally by the SDK and is disabled by default. Enabling MMAP can cause stream-open failures on some USB microphones.
- **USB device selection**: When a USB microphone is connected, it is detected and selected automatically.
- **Incompatible devices**: On some MediaTek-based TVs, opening the audio stream of a USB composite device (for example, DM30RGB) can fail.

### Echo Prevention
- Speech recognition is automatically blocked while the avatar is speaking.

### Playback Mode Trade-off (v0.12.0+)
- The default is **non-streaming** (`RuntimeConfig.audioNonStreaming = true`). Because the speech audio is played only after it has been fully received, mid-speech dropouts disappear but **the delay before the first sound increases**.
- If you need low latency, set it to `false`; on slow networks, however, buffer underruns can end speech prematurely (choppy playback).
- The value is captured when speech starts, so toggling it mid-speech does not affect the current utterance.

### Cached Speech Constraints (v0.12.0+)
- Works only in a session started with `play(useMelSpectrogram = true)`. Otherwise it returns `Result.failure(IllegalStateException)`.
- The audio format is fixed to **16 kHz mono int16 little-endian PCM** (cache contract). Other sample rates are not supported.
- Cached speech and server speech never play simultaneously — while one is in progress, the other waits or is interrupted.

## Known Issues

### 1. Memory Usage

Memory usage can be high during video processing and AI inference. In particular, calling `ResourceManager.init()` allocates **about 1 GB of native memory** for YUV frame buffers.

#### Buffer Lifecycle

`finish()` keeps the buffers so they can be reused immediately when re-entering the same avatar (0 ms). Complete memory release requires an explicit `deinit()` call.

| Scenario | Behavior |
|----------|------|
| Re-entering the same avatar | `init(same avatarId)` → buffers reused (0 ms) |
| Switching to a different avatar | `init(new avatarId)` → previous buffers released automatically + new allocation |
| App moved to background | `onTrimMemory` → `deinit()` → buffers released |
| App terminated | `CharacterActivity.onDestroy` → `deinit()` → fully released |
| Process force-killed | Reclaimed automatically by the OS kernel (no code needed) |

#### Required Implementation Patterns

**Application class — automatic memory release in the background:**
```kotlin
class MyApplication : Application() {
    override fun onCreate() {
        super.onCreate()
        registerComponentCallbacks(object : ComponentCallbacks2 {
            override fun onTrimMemory(level: Int) {
                if (level >= ComponentCallbacks2.TRIM_MEMORY_UI_HIDDEN) {
                    ResourceManager.deinit()
                }
            }
            override fun onConfigurationChanged(newConfig: Configuration) {}
            override fun onLowMemory() { ResourceManager.deinit() }
        })
    }
}
```

**SDK playback screen (ChatActivity, etc.):**
```kotlin
override fun onDestroy() {
    super.onDestroy()
    // finish() is a suspend function, so run it from a coroutine
    CoroutineScope(Dispatchers.Default).launch {
        klleonOndeviceSdk.finish() // Keeps buffers (waiting for reuse)
    }
}
```

**Avatar selection screen (CharacterActivity, etc.):**
```kotlin
override fun onDestroy() {
    super.onDestroy()
    // If the SDK is not playing (left before play), release memory manually
    if (!KlleonOndeviceSdk.playing) {
        ResourceManager.deinit()
    }
}
```

:::info Safe to call repeatedly
- `init()`: When called again for the same avatar (`avatarId`), existing buffers are reused (no duplicate allocation)
- `deinit()`: Safe to call multiple times (idempotent)
- `finish()`: Safe against duplicate calls thanks to the internal playing-state check
:::

### 2. Background Restrictions

Video processing is paused when the app moves to the background.


### 3. Single Instance Restriction

You must create **only one** `KlleonOndeviceSdk` instance per app.
Because internal coroutine scopes and thread pools are allocated per instance, creating multiple instances causes resource conflicts and memory leaks.

**Recommended: manage it as an object singleton**

```kotlin
// Share a single instance across the app
object SdkConfig {
    val sdk = KlleonOndeviceSdk()
}

// Usage in an Activity
class ChatActivity : ComponentActivity() {
    private val klleonOndeviceSdk = SdkConfig.sdk  // Reuse the same instance
}

class AnotherActivity : ComponentActivity() {
    private val klleonOndeviceSdk = SdkConfig.sdk  // Reuse the same instance
}
```

:::caution Caution
If you create `KlleonOndeviceSdk()` directly in an Activity field, a new instance is created every time the Activity is recreated (screen rotation, low memory, etc.), and the thread pools of previous instances accumulate.
:::

```kotlin
// Incorrect usage - multiple instances
class MainActivity : Activity() {
    val sdk1 = KlleonOndeviceSdk() // Instance 1
    val sdk2 = KlleonOndeviceSdk() // Instance 2 - conflict!
}
```

### 4. Screen Rotation

If the Activity is recreated on screen rotation, the SDK state may be reset.

**Solution:**
```xml
<!-- AndroidManifest.xml - handle screen rotation yourself -->
<activity
    android:name=".MainActivity"
    android:configChanges="orientation|screenSize|screenLayout" />
```

### 5. Android TV Specifics

- On TV platforms, layout changes can automatically give focus to the first focusable element, which may cause the keyboard to appear automatically.
- Block this at the source with `focusProperties { canFocus = false }` and enable focus only on click.
- Some USB audio devices may have compatibility issues on MediaTek-based TVs.

## Performance Optimization Tips

### GPU Acceleration

The SDK uses GPU acceleration by default. If problems occur on some low-end devices:

```kotlin
// Check the logs when GPU issues occur
adb logcat | grep "Klleon_"
```

### Battery Optimization

Battery consumption can be high during extended use:
- Call `finish()` when not in use
- Stopping processing when the screen turns off is recommended
- Use standby mode via `enterStandby()` / `exitStandby()`
